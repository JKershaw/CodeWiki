# Orchestrator and Executor Identifier Coordination

The orchestrator-executor system in this multi-agent documentation platform uses a two-tier identifier strategy for git commits. Each commit has both an internal UUID identifier (`id`) used for database relationships and a git SHA hash (`sha`) that corresponds to the actual git commit. The orchestrator creates work items with commit references, and the executor must process these work items to run agents against specific commits.

The orchestrator uses git SHAs when creating work items (`targetCommitId: commit.sha`), while agents internally operate on UUID-based commit records. This design choice stems from the fact that SHAs are the canonical, immutable identifiers in git systems, making them more reliable for cross-system references and external integrations. The executor translates SHAs to internal UUIDs using the `findBySha` repository method before passing commits to agents. This translation layer isolates agents from the specifics of how commits are identified externally while maintaining git-native references in the work queue.

The comment added to the orchestrator code explicitly documents this design decision: "Use SHA, not internal ID - executor looks up by SHA." This clarifies the contract between the orchestrator and executor components, preventing future confusion about which identifier type should be used in work items. The pattern follows a common architectural principle where external identifiers (git SHAs) are preserved at system boundaries while internal identifiers (UUIDs) are used for database integrity and relationship management.
