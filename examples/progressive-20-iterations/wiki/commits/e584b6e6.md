# Orchestrator and Executor Commit Identifier Coordination

The orchestrator and executor components use different identifier schemes when passing commit references through the work queue. The orchestrator generates work items that reference commits by their Git SHA (the 40-character hexadecimal hash from version control), while the executor requires internal UUID identifiers to look up commits in the repository. This architectural decision reflects a separation of concerns: the orchestrator operates at the Git/version control layer when deciding what work needs to be done, while the executor operates at the domain model layer when actually performing the work.

The coordination mechanism ensures type safety and correct lookups at each stage. When the orchestrator creates work items in `generateDeterministic()`, it sets `targetCommitId` to `commit.sha` rather than `commit.id`. The executor then performs a translation step in `executeWorkItem()` by calling `repos.commits.findBySha(repoId, workItem.targetCommitId)` to obtain the internal UUID before passing it to agents. This translation layer prevents the orchestrator from being tightly coupled to internal database identifiers while ensuring agents receive the correct internal references they expect.

The work queue's `WorkItem` domain object uses `targetCommitId: string | null` without constraining whether this field contains a SHA or UUID. This flexibility allows the work queue to serve as a boundary between the orchestration layer (which thinks in terms of Git SHAs) and the execution layer (which thinks in terms of internal domain IDs). The executor acts as an adapter, performing the impedance matching between these two identifier schemes. This design makes the system more maintainable because the orchestrator can generate work based on Git operations without knowing about database internals, and agents can work with stable internal identifiers without worrying about Git SHA lookups.

## Key Findings

- **ARCHITECTURE** (high): Orchestrator uses Git SHAs for commit references while executor translates to internal UUIDs, creating clean separation between Git and domain layers
- **DATA_FLOW** (high): Work items flow through queue with SHA identifiers, then executor performs findBySha() lookup to obtain internal UUID before agent execution
- **INTERFACE** (medium): WorkItem.targetCommitId field is string type that accepts both SHAs and UUIDs, serving as boundary between layers
- **PATTERN** (medium): Adapter pattern used in executor to translate between identifier schemes, preventing tight coupling
- **ERROR_HANDLING** (medium): Executor fails work item gracefully when SHA lookup fails, preventing cascade failures
